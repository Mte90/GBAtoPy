## IRQ Probe Module

### `probe/irq_probe.py` — Comprehensive IRQ State Capture

**Purpose:** Single-shot IRQ debugging that captures ALL relevant state in one run, per AGENTS.md rule 45.

**Background:** When debugging IRQ-related blank screens or crashes, the manual workflow required 5+ sequential probe rounds to capture all relevant state (PC, LR, CPSR mode, T bit, R0-R3, R12, IME, IE, IF, _irq_return_pc). This module automates that into a single comprehensive snapshot.

**What it provides:**

1. **`irq_entry_snapshot(registers, cpsr, memory, instruction_count, frame_count)`** — Captures ALL state at IRQ entry:
   - PC, LR, SP (R13), R0-R3, R12
   - CPSR: mode (hex), N/Z/C/V/I/F/T bits
   - IME, IE, IF (both raw and decoded — which IRQs are pending/enabled)
   - DISPSTAT (decoded: VBlank/HBlank/VCounter bits)
   - DISPCNT (decoded: mode, forced_blank, BG enables)
   - _cpu_halted, _halt_reason, _irq_return_pc
   - instruction_count, frame_count

2. **`irq_exit_snapshot(registers, cpsr, memory, _irq_return_pc)`** — Captures state at IRQ handler return:
   - PC (should match _irq_return_pc)
   - CPSR mode (should be back to User/System, not IRQ 0x12)
   - T bit (should match pre-IRQ state)
   - R0-R3, R12 (should be restored)
   - Any discrepancy from expected values

3. **`format_irq_flags(ie, if_reg)`** — Decodes IE/IF bit flags:
   - Bit 0: VBlank
   - Bit 1: HBlank
   - Bit 2: VCounter
   - Bit 3-6: Timer 0-3
   - Bit 7: Serial
   - Bit 8-11: DMA 0-3
   - Bit 12: Keypad
   - Bit 13: Gamepak (RTC)

4. **`install_irq_probes(transpiled_code_path, output_path)`** — Auto-instruments a transpiled .py file:
   - Reads the transpiled file
   - Inserts probe calls at _deliver_irq entry and exit points
   - Writes the instrumented version to output_path

**Usage:**

```python
# Import the probe functions
from scripts.probe.irq_probe import irq_entry_snapshot, irq_exit_snapshot, install_irq_probes

# Manual snapshot capture (e.g., in a transpiled ROM's _deliver_irq handler)
snapshot = irq_entry_snapshot(registers, _cpsr, memory, _instruction_count, _frame_count)
print(snapshot)

# Auto-instrument a transpiled ROM
install_irq_probes('/tmp/rom.py', '/tmp/rom_instrumented.py')

# Run the instrumented version
# python3 /tmp/rom_instrumented.py --headless --frames 60
```

## Test Scripts

### `tests/test_cfg_regression.py` — CFG Explosion Regression Test

**Purpose:** Verify that the CFG (Control Flow Graph) builder doesn't "explode" by following linear data walks and producing 50K+ reachable addresses.

**Background:** The CFG builder had a bug where it would traverse data regions as if they were code, creating a massive number of basic blocks. The fix introduced:
- A global fall-through budget (50K addresses max)
- Max consecutive invalid instructions limit (16)

**What it tests:**
- ✅ Transpilation completes successfully (no hang, no crash)
- ✅ Transpilation completes in reasonable time (< 60 seconds per ROM)
- ✅ Output is valid Python (compiles with `py_compile`)
- ✅ Function count is reasonable (< 50K functions)

**Test ROMs:** combo.gba, hyperspace-roll.gba, the-purple-night.gba (complex ROMs that would trigger CFG explosion)

**Usage:**
```bash
# Run all CFG regression tests
python3 -m pytest tests/test_cfg_regression.py -v

# Run a single ROM test
python3 -m pytest tests/test_cfg_regression.py::test_cfg_does_not_explode[combo.gba] -v

# With verbose output showing timing and function counts
python3 -m pytest tests/test_cfg_regression.py -v -s
```

**Expected output:**
```
combo.gba: PASS (transpile_time=2.11s, functions=48,455)
hyperspace-roll.gba: PASS (transpile_time=1.22s, functions=39,035)
the-purple-night.gba: PASS (transpile_time=1.06s, functions=27,656)
```

**Location:** `tests/test_cfg_regression.py`

### `run_tests.py` — Unified 3-Level Test Runner

**Purpose:** Single command for full verification at three levels — syntax, execution, and visual comparison.

**Test Levels:**

| Level | What it verifies | What it does NOT verify |
|-------|------------------|--------------------------|
| 1 (syntax) | Transpile ROM + `py_compile` passes | Graphics, audio, execution behavior |
| 2 (execution) | Generated script runs headless without crash | Correct graphics/audio output |
| 3 (visual) | Screenshot matches mGBA golden (pixel diff < threshold) | Gameplay logic, audio accuracy |

**Usage:**
```bash
# Level 1 only (default — same scope as run-all-tests.sh)
python3 scripts/run_tests.py

# Levels 1+2 (syntax + execution)
python3 scripts/run_tests.py --level 2

# Levels 1+2+3 (full visual verification)
python3 scripts/run_tests.py --level 3

# Single ROM
python3 scripts/run_tests.py --rom hello --level 3

# Filter by name
python3 scripts/run_tests.py --filter mode3 --level 2

# Parallel workers (default: 1 = serial)
python3 scripts/run_tests.py --workers 8

# Custom frame count for execution
python3 scripts/run_tests.py --level 2 --frame 120

# Extended stability testing (300 frames)
python3 scripts/run_tests.py --level 2 --frames 300
python3 scripts/run_tests.py --level 2 --long-run  # convenience flag for 300 frames

# Save JSON report to specific path
python3 scripts/run_tests.py --level 3 --json test-reports/report.json

# Skip building the transpiler (use existing binary)
python3 scripts/run_tests.py --no-build
```

**Output:** Per-ROM per-level status in console + timestamped JSON report in `test-reports/`.

**Note:** Level 3 requires golden screenshots to exist in `test-reports/goldens/`. Use `generate_goldens.py` to create them. ROMs without goldens are reported as `no_golden` (not a failure).

### `audio/capture_transpiled.py` — Transpiled Audio Capture

**Purpose:** Capture audio from a transpiled GBA ROM Python file and write to a 16-bit stereo WAV file at 44100Hz.

**What it does:**
- ✅ Import a transpiled ROM module (standalone Python file)
- ✅ Access the global `apu` instance from the module
- ✅ Call `apu._generate_samples()` in a loop for N frames
- ✅ Convert 8-bit unsigned samples to 16-bit signed
- ✅ Write to WAV file with proper RIFF header

**Requirements:**
- The transpiled ROM must expose a global `apu` instance from `gba_runtime.apu`
- The APU must have a `_generate_samples(count)` method that returns raw audio bytes

**Usage:**
```bash
# Capture 300 frames (~5 seconds) - default
python3 scripts/audio/capture_transpiled.py /tmp/stripes.py /tmp/stripes_audio.wav

# Custom frame count (e.g., 60 frames = ~1 second)
python3 scripts/audio/capture_transpiled.py /tmp/hello.py /tmp/hello.wav --frames 60

# Longer capture (600 frames = ~10 seconds)
python3 scripts/audio/capture_transpiled.py /tmp/mode3.py /tmp/mode3.wav --frames 600
```

**Output:** 16-bit stereo WAV file at 44100Hz

**Example workflow:**
```bash
# 1. Transpile ROM
cargo run -p gbatopy-cli -- pipeline --rom test_roms/roms/stripes.gba --output /tmp/stripes.py

# 2. Capture golden audio from mGBA
./scripts/audio/capture_golden.sh --rom test_roms/roms/stripes.gba --frame 300 --output /tmp/stripes_golden.wav

# 3. Capture audio from transpiled ROM
python3 scripts/audio/capture_transpiled.py /tmp/stripes.py /tmp/stripes_transpiled.wav --frames 300

# 4. Compare audio
python3 scripts/verify/compare_audio.py /tmp/stripes_golden.wav /tmp/stripes_transpiled.wav
```

### `run_audio_tests.py` — Audio Spectral Test Runner

**Purpose:** Orchestrates the existing capture/compare pipeline across all audio-capable ROMs. For each ROM: transpile → capture transpiled audio → capture mGBA golden → spectral compare. Reports per-ROM pass/fail/skip with diff percentage.

**What it does:**
- ✅ Reads ROM list from `test-roms-config.toml` — filters by `"audio"` in features
- ✅ For each audio ROM:
  - Checks ROM file exists in `test_roms/roms/` — SKIP if missing
  - Transpile: `./target/release/gbatopy transpile <rom> --output /tmp/<rom>_audio.py`
  - Capture transpiled audio: `python3 scripts/audio/capture_transpiled.py <transpiled.py> <output.wav> --frames 300`
  - Capture golden audio: `bash scripts/audio/capture_golden.sh <rom> --frame 300 --output <golden.wav>`
  - Compare: `python3 scripts/verify/compare_audio.py <golden.wav> <transpiled.wav>`
  - Record result: PASS/FAIL/SKIP + diff percentage + duration
- ✅ Handles errors gracefully:
  - Transpile failure → FAIL with stderr
  - Capture timeout (30s per step) → FAIL with "timeout"
  - Compare SKIP (both silent) → SKIP with "both silent"
  - Missing ROM file → SKIP with "ROM not found"
- ✅ Reports summary:
  - Per-ROM table: name, status, diff%, duration, notes
  - Summary: X PASS, Y FAIL, Z SKIP out of N total
  - Exit code: 0 if all PASS, 1 if any FAIL, 2 if all SKIP

**Usage:**
```bash
# List all audio-capable ROMs
python3 scripts/run_audio_tests.py --list

# Test a single ROM
python3 scripts/run_audio_tests.py --rom helloAudio

# Test with verbose output
python3 scripts/run_audio_tests.py --rom helloAudio --verbose

# Test with custom frame count

# Write results to file
python3 scripts/run_audio_tests.py --rom helloAudio --output /tmp/audio_report.txt

# Run all audio ROMs (batch mode)
python3 scripts/run_audio_tests.py
```

**Exit codes:**
- `0` — All PASS (or single ROM PASS)
- `1` — Any FAIL (or single ROM FAIL)
- `2` — All SKIP (or single ROM SKIP, or no audio ROMs found)

## Verification Tiers

The verification tier system provides graduated gates for different stages of the development cycle.

### `tiers.sh` — Tiered Verification Runner

**Purpose:** Unified entry point for all verification levels, from fast syntax checks to full regression suites.

**Usage:**
```bash
# T0: Fast pre-commit gate (fmt + clippy + pytest)
./scripts/verify/tiers.sh t0

# T1: Single ROM canary (default: stripes)
./scripts/verify/tiers.sh t1 hello

# T2: 8-ROM gate (parallel, pre-commit)
./scripts/verify/tiers.sh t2

# T3: Full 91-ROM sweep
./scripts/verify/tiers.sh t3

# All: Run T0 + T1 + T2 (excluding T3)
./scripts/verify/tiers.sh all
```

**Tier Definitions:**

| Tier | What it runs | When to use | Expected time |
|------|--------------|-------------|---------------|
| **T0** | `cargo fmt --check` + `cargo clippy --all-targets` + `pytest runtime tests` | After every code change, before committing | < 60s |
| **T1** | Single ROM Level 3 test (visual comparison) | Canary test after codegen/runtime fix | ~30s |
| **T2** | 8 gate ROMs in parallel (4 workers): stripes, mode3, mode4, window_midframe, sprite-hmosaic, song, cascade7, hello | Pre-commit gate — blocks commit if any fail | ~2-3 min |
| **T3** | Full 91-ROM Level 3 sweep | End of session, before major commits | ~15-20 min |
| **all** | T0 + T1 + T2 (sequential) | Quick full verification without the long T3 sweep | ~3-5 min |

**Gate ROMs (T2):**
These 8 ROMs form the pre-commit gate. If any regress, the commit is blocked:
- `stripes` — Basic 4BPP background test
- `mode3` — Mode 3 (320x240) rendering
- `mode4` — Mode 4 (240x160) rendering
- `window_midframe` — Window clipping test
- `sprite-hmosaic` — Sprite + horizontal mosaic
- `song` — APU audio channel test
- `cascade7` — Timer cascade test
- `hello` — Basic ARM instruction test

**Exit codes:**
- `0` — All tests pass
- `1` — One or more tests fail
- `2` — Usage error (invalid tier, missing arguments)

**CI Integration:**
The script is CI-callable: non-interactive, proper exit codes, color disabled when not a TTY.

```yaml
# Example GitHub Actions usage
- name: Run T0 gate
  run: ./scripts/verify/tiers.sh t0
  
- name: Run T2 pre-commit gate
  run: ./scripts/verify/tiers.sh t2
```

### `verify_input.py` — Input Register Verification

**Purpose:** Inject programmed keypresses into transpiled ROMs and verify the KEYINPUT register (0x04000130) returns the expected values.

**What it does:**
- ✅ Parse a key sequence file (frame-based button injection)
- ✅ Generate a hook script that injects input at specified frames via `input_instance.update_keys()`
- ✅ Log KEYINPUT register reads to a file for verification
- ✅ Transpile the ROM using the Rust CLI
- ✅ Run the transpiled ROM with the hook script
- ✅ Verify that KEYINPUT reads match expected values
- ✅ Report PASS/FAIL with detailed frame-by-frame results

**Key sequence file format:**
```text

20: A,B
30: A,B,C
```

Valid buttons: `A`, `B`, `START`, `SELECT`, `UP`, `DOWN`, `LEFT`, `RIGHT`, `R`, `L`

### `audit_pc_masking.py` — PC-Write Masking Audit (Invariant #6)

**Purpose:** Scan Rust codegen source files to verify all generated Python code that writes to `registers[15]` (PC) includes proper bit 0 masking.

On GBA/ARM architecture, bit 0 of a PC value is the T bit (Thumb/ARM mode selector). Unmasked PC writes can cause the CPU to execute in the wrong mode, crashing the transpiled output.

**What it checks:**
- ✅ Scans all `.rs` files in `crates/gbatopy-cli/src/codegen/instruction_codegen/`
- ✅ Scans all `.py` template files in `crates/gbatopy-cli/assets/templates/`
- ✅ Finds all `registers[15] =` assignments in generated code strings
- ✅ Verifies masking patterns: `& 0xFFFFFFFE`, `& 0xFFFFFFFC`, or variable-based masks
- ✅ Classifies instruction type (LDM, POP, Branch, Exception Return, Data Processing, etc.)
- ✅ Reports unmasked paths with file:line, instruction type, and context

**Valid masking patterns:**
- `& 0xFFFFFFFE` — Clear bit 0 (Thumb mode)
- `& 0xFFFFFFFC` — Clear bits 0-1 (ARM mode alignment)
- `_pc_val & 0xFFFFFFFE`, `_new_pc & 0xFFFFFFFE`, etc. — Variable-based masks

**Usage:**
```bash
# Run the audit
python3 scripts/audit_pc_masking.py

# Use as a CI gate
python3 scripts/audit_pc_masking.py && echo "All PC writes masked"
```

**Exit codes:**
- `0` — All PC writes are properly masked
- `1` — One or more unmasked PC writes found
- `2` — Usage error
